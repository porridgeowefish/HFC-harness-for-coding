01 · 交付结构

冷启动体系构成

冷启动后，AI 不再只看代码，也不会把所有文档塞进上下文。它按任务装配规则和事实，按 workflow 保留过程，按 Hook / CI 处理可确定的违规。

顶层 Rules

规定项目必须怎样做：架构边界、工程约定、测试、API / 数据、提交与 MR。

.codebuddy/rules/

工程知识

说明工程怎样组织、代码在哪、架构为何如此；作为按需导航，而非源码副本。

docs/knowledge/

业务知识

记录当前功能、业务规则与必要演变历史；验收后成为后续需求的默认事实。

docs/function/

Workflow 档案

从原始材料到 MR 的完整事务边界；自然语言每次只推进 state 指定的一个节点，不能用模糊描述跳过需求确认。

docs/workflows/<task-id>/
唯一原则： Rules 约束行为；知识解释事实；workflow 保存本轮过程；Hook / CI 只执行可确定判断。四者不互相替代。
02 · 文件结构

文件按读者、时效和责任分区。

人读产物放进 docs/ 并纳入 Git；机器运行态放进 .codebuddy/workflows/，默认不混入业务提交。每一次需求到 MR 都只对应一个 workflow 目录。

03 · 知识库与 Rules

知识库与 Rules 模块

工程知识、业务知识和 Rules 的职责不同：知识库回答“系统事实是什么”，Rules 回答“本轮开发必须遵守什么”。下面按文件层级展开每一部分。

ENGINEERING KNOWLEDGE

工程知识库

用于定位工程入口、理解结构与架构取舍；不复制源码实现细节。

  • 项目总览.md：用途、技术栈、软件设计架构、启动/构建/测试入口、顶层模块和事实依据。
  • 文件树.md：先生成全量路径骨架；随后由分区负责人逐个阅读并回写每项真实用途。
  • 业务入口.md：业务问题 → 业务知识、工程知识和源码/配置入口。
  • architecture/：可版本化的 component.puml 与面向人的 component.svg。
  • modules/<模块>.md：模块定位、目录与入口、核心组成、主要流程、跨端关系、兼容边界、生效机制、易误判点、事实依据。
FUNCTION KNOWLEDGE

业务功能知识库

用于理解当前系统能力和规则。新需求默认先读当前功能描述，必要时再读演变历史。

  • module.json：业务模块 ID、名称、别名、目录定位。
  • function.json：模块内功能点 ID 与目录映射。
  • 功能描述.md：当前有效功能、业务规则、边界和主要流程。
  • 功能演变历史.md：验收后的关键变化、当时问题和必要取舍。
  • 验收后由 knowledge-update-review.md 审核是否回写。
TOP-LEVEL RULES

Rules 模块

按任务强制装配。每份规则固定写适用场景、必须遵守、相关知识入口、验证方式和更新门槛；Rules 不复制知识正文。

  • architecture.md：依赖方向、组件边界、跨层访问。
  • engineering.md：模块职责、目录、错误处理、公共能力。
  • testing.md：测试层次、数据、验收和覆盖要求。
  • api-and-data.md：接口兼容、数据一致性、迁移与持久化。
  • commit-and-mr.md：提交、报告、MR 与审核前提。
规则文件何时加载必须规定主要验证何时更新
architecture.md新建模块、跨模块变更、重构依赖方向、组件边界、跨层访问、共享契约设计结论、独立评审、结构性门禁架构边界或不可破坏取舍发生变化
engineering.md新增或修改工程实现模块职责、目录归属、异常处理、公共能力复用设计对齐、代码评审、项目现有检查形成跨任务稳定工程约定
testing.md行为变化、修复、新增测试测试层次、测试数据、验收表达、最低覆盖要求开发摘要、门禁、需求—验证映射团队测试策略或约束发生稳定变化
api-and-data.md接口、数据模型、迁移、持久化变化兼容性、迁移、数据一致性、对外契约设计结论、迁移验证、安全/独立评审接口或数据规约被正式调整
commit-and-mr.md提交、创建/更新 MR、报告生成提交边界、MR 前提、报告绑定 Commit、审核要求Hook、CI required check、平台审核协作流程或平台契约变化
规则文件的固定骨架任何规则都按相同字段写，动态事实必须由项目探索填充。

适用场景

写可判定的触发条件，不写“通用”“随时”。例如任务类型、变更范围或行为类别。

必须遵守

写边界、禁止事项和共享契约；不复述具体项目文件或一次性实现。

验证与更新

明确由设计、测试、独立评审或确定性门禁验证；写明何时才能更新本规则。

规则装配表主流程根据当前任务，把必要规则放进节点输入，而不是等待模型“想起来”。

设计节点

加载 architecture、engineering，以及需求范围匹配的 API / 数据规则。

开发节点

加载任务包指定的规则；写测试时强制加载 testing。

评审节点

加载本轮设计与实现实际涉及的规则，作为独立评审的判断基线。

规则更新门槛不是每次改代码都改 Rules。局部经验必须先留在 workflow，再判断是否升格。

可进入 Rules

跨任务、长期稳定、必须遵守；违反会造成架构越界、契约破坏或团队协作失效。

只进入知识

解释性事实、架构原因、模块边界、易误判点；需要判断，但不应每次强制约束。

只留在 workflow

一次性修复、局部路径、临时故障、未验证经验和当前任务的对话过程。

04 · 0.8.0 初始化与契约编排

先建树，再按事实动态分工。

主 Agent 先让侦察 subagent 扫描全部可见文件和目录并写路径骨架；随后按实际模块和依赖分发工程、业务、汇总与 Rules subagent。每个可读路径只有一个负责人，负责人直接写自己的文档和树项用途；汇总与 Rules 任务等待上游完成，失败任务由主 Agent 重派。初始化结束后，顶层 Skill 用自然语言逐项引导管理员完成八项 checklist，再由 Git 提交共享契约。

结构合同：项目总览在技术栈之后固定有“软件设计架构”；工程模块包含九段信息；功能描述包含当前状态和事实依据；Rules 包含必须遵守、相关知识入口、验证方式、更新门槛。模板动态值只能使用声明的 <...>，完成态不保留占位符。未初始化项目的 Hook 完全 no-op。设计阶段新增共同开发契约，所有开发任务读取同一正文。

06 · 节点之间管理

节点与状态管理

节点不是聊天轮次，而是可恢复的流程状态。主流程只能消费已落盘产物；人工确认必须进入状态；新 Commit 会让关联报告和批准失效。

需求：把原始诉求变成正式业务基线

这是唯一允许吸收原始材料和人类业务裁定的节点。没有发布的正式需求，后续节点不得开工。

输入

原始材料、相关业务功能知识、匹配的顶层 Rules。

输出

材料索引、候选评审稿、正式需求单。

放行门槛

至少一项正式需求；每项有业务级验收；需求发布已确认。

回退

角色、业务价值、范围或验收标准不清；设计发现业务冲突无法裁定。

人工动作：审核候选并发布正式需求。状态写入 approvals.requirement_published。

设计：把业务基线变成执行契约

设计先探索事实，再暴露需要人裁定的问题。对齐稿可讨论；设计结论、共同开发契约和任务包只保留已确认内容。

输入

正式需求、工程/业务知识、源码与配置、按任务装配的 Rules。

输出

设计对齐稿、设计结论、共同开发契约、任务包。

放行门槛

无待确认关键决策；契约清单与按需块一致；任务契约 ID 均存在；三份设计产物已提交且工作区干净；任务包基于该 Git 版本确认开工。

回退

共同开发契约未定、任务不可验收或确认后的设计产物变化时回设计；业务目标不清回需求。

人工动作：只裁定关键业务/技术问题，并确认任务包开工；版本追溯只使用 Git。

开发：用可复核证据替代过程口头说明

任务按验收标准先表达测试，再最小实现、集成并运行项目已有门禁。未配置能力必须如实标记。

输入

正式需求、设计结论、共同开发契约、完整任务包、目标源码与测试、匹配 Rules。

输出

实际代码变更、开发摘要、门禁结果与逻辑证据引用。

放行门槛

已声明门禁结果可复核；未完成项透明；人工复核提交 MR。

回退

门禁失败留在开发；需改范围或共同开发契约时退回设计并重新确认任务包。

人工动作：整轮结果出来后复核是否创建/更新 MR，不逐任务接管实现。

评审：由独立上下文审最终代码快照

reviewer 只读、独立，不接收开发对话，不直接改代码。评审只对当前 Commit 有效。

输入

MR Diff、正式需求、设计结论、任务包、开发摘要与门禁证据。

输出

结构化 findings、安全扫描结果、最终代码合并报告。

放行门槛

无 BLOCKER；报告绑定最终 Commit；平台原生审核通过。

回退

BLOCKER 回开发；新 Commit 使当前评审与报告失效，重新评审。

人工动作：沿用原代码平台的审批，不建设额外 AI 审批。

知识回写：独立审核长期资产，而不是附注在 merge report

它回答“这次变更是否改变了系统的长期事实”，而合并报告只回答“当前代码快照是否可合并”。

输入

需求、设计、Diff、验证证据、独立评审结果。

输出

长期知识更新审核单、批准后的长期资产更新。

放行门槛

每项长期资产已判定；无待人裁定；负责人已审核。

回退

审核退回修改；知识更新产生新 Commit 后，回评审节点。

人工动作：审核哪些知识和 Rules 应更新。通过后实际回写，并重新独立评审最终快照。
07 · 系统适配

系统适配流程

系统适配的本质是一个负责人友好的交互流程：系统先展示已识别信息，负责人只校正差异与决定风险边界，最终把确认结果写入仓库契约。

01 · DISCOVER

识别原有体系

系统先从仓库和既有协作资产中提取事实，不要求用户从零描述项目。

  • 代码仓、分支、MR / PR 与审核人
  • 构建、测试、扫描、CI required check
  • 现有需求、设计、架构、接口和业务文档
  • 已存在的责任边界与发布路径
02 · MAP

映射到 Harness 资产

系统展示“已有资产将如何被复用”，负责人确认归属而不是重新写文档。

  • 工程事实 → docs/knowledge/
  • 业务事实 → docs/function/
  • 团队规约 → .codebuddy/rules/
  • 可执行门禁 → .codebuddy/harness.json
03 · CONFIRM

确认不确定项

界面只抛出系统无法确认、但需要负责人判断的少数问题。

  • 识别结果是否正确
  • 门禁是否保留、是否 required
  • 文档是事实、规则还是失效内容
  • 责任人、平台接入和暂不处理项
04 · PROVE

用真实事务验证

选择一个范围可控的真实需求，验证接入不是“文件生成成功”，而是真正能跑完整事务。

  • 状态是否可恢复
  • 节点是否读取正确资产
  • 门禁与证据是否能复核
  • 知识是否在合并前被独立审核
08 · 系统管理员接入 Checklist

系统管理员接入检查

系统管理员只检查三类接入事实：上下文和外部系统如何供数/出数，知识库与 Rules 是否准确完整，模板和素材是否足以跑完整事务。三类检查通过后，Harness 才可初始化首个 workflow。
