# V0.7 分布式初始化与 Markdown 合同

## 状态

**历史版本，已被 0.8.0 取代。** 本文只用于追溯 0.7.0 的初始化设计；凡涉及 workflow 文件集合、设计到开发交接或共同契约的内容，均以 `2026-09-10-v08-shared-development-contract.md`、`ADR-latest.md` 和现行技术设计为准，不再构成当前插件合同。

本文曾由项目负责人确认并在 0.7.0 实施。当时它替代第六版中“单一宿主 Agent 读完全仓并提交单份知识草案”的初始化编排方式；其中 Git 协作和不使用 digest/hash/CAS 的决定仍被后续版本继承。

## 目标

初始化由主 Agent 动态分发多个专职 subagent 完成。subagent 直接写入其唯一负责的长期文档，不增加草案审核回合。主 Agent 只负责全量扫描、依赖图、文件所有权、任务调度、失败重派和最终结构校验。prepare、subagent 回写和 finalize 属于同一顶层编排会话；脱离会话的 CLI finalize 对已有长期资产按冲突处理，不能用未持久化的清单覆盖。

初始化完成时，除按需创建的 workflow 外，所有规范长期资产必须已由项目事实填实：工程知识、业务知识、架构源图与 SVG、Rules、共享配置和 checklist。使用者只需自然语言提出接入请求与回答 checklist，不需要理解内部命令、JSON 草案或 subagent 分工。

## 不可变边界

- 只允许规范目录：`docs/knowledge/`、`docs/function/`、`docs/workflows/`、`.codebuddy/`；不创建 `gates.md`、`harness-self.md`、`核心约束.md`、`启动入口.md` 或任何未登记的辅助 Markdown。
- 初始化开始先全量枚举所有可见文件和目录；只排除 `.git`、`node_modules` 与 `.codebuddy/workflows/`。不得把 README、既有 docs、常见源码目录或扩展名当作唯一材料位置。
- 每个可读文件必须被某个 subagent 分配和读取；二进制、无法读取或符号链接保留在文件树，并明确标注其性质和不可读取原因。
- 初始化不创建 workflow，不写 workflow 正文，也不要求负责人审核各 subagent 的中间成果。
- 文档版本交给 Git 管理；不添加 digest、内容哈希、CAS、跨进程初始化锁或第二套确认链。
- 一名管理员串行发起初始化并提交结果；其他成员只拉取共享契约，不重复初始化。

## 初始化编排模型

### 主 Agent：调度者，不是总撰稿人

主 Agent 不读取全仓源码后自己撰写所有文档，也不收集草案后逐篇审核。它维护一次初始化会话中的内存任务图：已发现的文件、文件归属、上游依赖、每个 subagent 的唯一写入路径和完成状态。该任务图是会话控制数据，不在业务仓库新增文件。

主 Agent 必须保证两条规则：一是每个可读文件恰好分配给至少一个阅读任务；二是同一时刻两个 subagent 不得写同一文件或同一 JSON 索引。任一任务失败时，主 Agent 只重派该任务及其未开始的下游任务，不回滚已完成且仍然依赖有效的其他分区。

### 动态任务图：固定约束，不固定教程

任务类别由实际文件树决定，不按预先写死的“前端、后端、数据库”教程拆分。一个纯脚本项目可以只有侦察、单模块写入、汇总和 Rules 四个任务；多服务、多端项目可以按服务、端、领域或共享库拆为多个并行任务。

唯一固定的依赖关系如下：

```text
全量树与侦察地图
  ├── 工程分区写入（可并发）
  └── 业务分区写入（可并发）
          ↓
项目总览、架构图、业务入口（依赖相关分区成果）
          ↓
Rules（依赖已落盘知识入口）
          ↓
结构与引用校验、checklist 引导、Git 提交提示
```

`文件树.md` 是侦察任务写入的第一份长期 Markdown，也是后续所有任务的唯一文件导航。侦察阶段先写完整路径骨架；每个分区 subagent 在实际阅读其归属文件后，必须回写对应树项的真实用途。汇总任务只能在所有可读文件的树项均已回写后写项目总览、业务入口或 Rules。

### subagent 写入职责

| 角色 | 必读输入 | 唯一写入范围 | 输出给主 Agent |
| --- | --- | --- | --- |
| 侦察 subagent | 全量文件树、已有文档、启动/构建/配置入口 | `docs/knowledge/文件树.md` 的完整路径骨架 | 模块划分、业务域、依赖关系、每个可读文件的阅读归属 |
| 工程分区 subagent | 分配的全部源码/配置/文档与文件树 | 自己拥有的 `docs/knowledge/modules/<工程模块>.md`，以及归属树项的用途回写 | 已覆盖路径、真实用途、模块关系、汇总依赖 |
| 业务分区 subagent | 分配的业务相关文件、已有业务材料与工程入口 | 自己拥有的 `docs/function/<业务模块>/`，以及归属树项的用途回写 | 已覆盖路径、真实用途、功能点、汇总依赖 |
| 汇总 subagent | 文件树、完成的工程/业务文档、架构相关源码 | `项目总览.md`、`业务入口.md`、`architecture/component.puml`、`architecture/component.svg` | 已使用的知识路径、未识别事实 |
| Rules subagent | 已完成的项目总览、架构图、模块/功能知识 | `.codebuddy/rules/` 的五个固定文件 | 每份 Rule 的知识入口与验证依据 |

一个 subagent 可以承担多个角色，仅当其写入范围仍然互不重叠且上游输入齐全。主 Agent 不得让“工程分区”和“汇总”任务并发修改同一架构或导航文件。

### 机器边界与最终校验

自然语言入口在内部使用三个受控运行时边界：

1. `init` 发现项目并准备共享配置与目录，但不生成完成态占位文档；
2. subagent 根据动态任务图直接写各自拥有的 Markdown、图与索引；
3. `init` 完成校验确认所有规范资产存在、格式正确、引用可达、checklist 完整，然后提示管理员提交 Git。

第三步是确定性结构校验，不是对 subagent 内容的人工审核。校验失败时主 Agent 将错误交给拥有该文件的 subagent 修复；不会由主 Agent 悄然改写其事实结论。

## 统一 Markdown 合同

### 通用规则

- 业务仓库生成的 Markdown 使用 UTF-8、单个 H1、固定章节顺序与相对项目根目录路径。
- 模板中的动态值只能出现为合同声明的 `<...>` 占位符；初始化完成后的文档不得出现任何 `<...>`、`待确认`、`用途待确认` 或伪造的示例事实。
- 每一份工程或业务知识文档都必须指向支撑其结论的仓库内相对路径；找不到证据的事实必须列入 `未识别项`，不能编造。
- 表格的标题行、列顺序和分隔行是合同的一部分；工具可追加数据行，不得改写表头。

### 常驻入口与工程知识

`CODEBUDDY.md` 固定为：

```md
# 项目导航

## 阅读顺序与上下文边界

## Rules 装配索引

## 全局行为规则
```

它只保存阅读边界、操作到 Rules 的装配索引和全局行为规则，不保存项目业务事实或复制 Rules 正文，且不超过 200 行。

`docs/knowledge/项目总览.md` 固定章节顺序：

```md
# 项目总览

## 项目用途

## 技术栈

## 软件设计架构

## 启动、构建与测试入口

## 顶层模块

## 未识别项

## 事实依据
```

“软件设计架构”位于技术栈之后，至少含架构风格、分层/组件、依赖方向、主要请求或数据流、关键边界和架构图引用。

`docs/knowledge/文件树.md` 仅含标题、固定说明和树形行。初始化中的第一轮骨架行只允许写为 `- \`相对路径\``，子项缩进两个空格、目录以 `/` 结尾；它只服务于全量分工，不填任何泛化说明。初始化完成态的每一行必须回写为 `- \`相对路径\` — 一句真实用途说明`。它列出全量可见目录和文件，而非“关键文件列表”。每一个可读文件和目录都必须被其负责 subagent 回写为基于实际阅读的具体用途。不得以“业务逻辑”“配置文件”“源码目录”“目录用途”“用途待确认”等泛化文字代替真实内容；二进制、符号链接和不可读文件则明确写出其类别及不可读取原因。

`docs/knowledge/业务入口.md` 固定为以下表格，不复制业务规则和 Rules 正文：

```md
# 业务入口

仅负责从业务问题定位业务知识、工程知识和源码入口，不复制 Rules 正文。

| 业务问题/场景 | 业务模块/功能点 | 优先阅读的业务知识 | 工程知识入口 | 源码/配置入口 |
| --- | --- | --- | --- | --- |
```

`docs/knowledge/modules/<工程模块>.md` 固定章节顺序：

```md
# <工程模块名称>

## 模块定位

## 目录与入口

## 核心组成

## 主要流程

## 跨端关系

## 兼容边界

## 生效机制

## 易误判点

## 事实依据
```

其中“跨端关系、兼容边界、生效机制、易误判点”保留为必填维度；前四个模块章节使它成为具体模块档案，而不是只有四条抽象提醒。

### 业务知识

`docs/function/<业务模块>/<功能点>/功能描述.md` 固定为：

```md
# <功能点>

- 所属业务模块：<业务模块>
- 当前状态：<当前有效/已废弃>

## 当前功能

## 业务规则

## 边界

## 主要流程

## 事实依据
```

`功能演变历史.md` 有历史记录时，每条记录使用日期标题和四个字段：已验收变化、当时问题、必要取舍、任务记录。没有已验收历史时，文件只能说明“当前没有已验收的历史变化；首次建档依据见同目录的 `功能描述.md`”，不得伪造初始化变更记录。

`module.json` 与 `function.json` 继续只做轻量定位索引，不复制 Markdown 正文；每个确认存在的业务模块都有 `function.json`，每个功能点都有上述两份 Markdown。

### Rules 与知识入口

五份固定 Rules 均使用同一结构：

```md
适用场景: <具体操作触发条件>

# <规则名称>

## 必须遵守

## 相关知识入口

## 验证方式

## 更新门槛
```

Rules 是“执行约束 + 知识索引”。`相关知识入口` 必须使用存在的相对路径链接到 knowledge/function/source，而非复制知识正文；`业务入口.md` 则面向业务问题导航。二者分别回答“这一类操作怎么做”和“这个业务问题从哪里理解”。

### Workflow

> 历史口径（已失效）：0.7.0 当时使用十个 workflow 文件。0.8.0 已在 `design-decision.md` 与 `task-package.md` 之间加入 `development-contract.md`，当前必须使用十一文件集合；本段不得作为实现或验收依据。

## 模板与运行时数据合同

初始化子任务使用结构化内部数据，但不要求用户编辑 JSON。新合同拒绝旧的 `{ name, summary }` 工程模块对象和仅包含字符串数组的 `ruleAdjustments`。

工程模块数据至少包含：名称、模块定位、目录与入口、核心组成、主要流程、跨端关系、兼容边界、生效机制、易误判点、事实依据。功能数据至少包含：所属模块、当前功能、业务规则、边界、主要流程、工程入口和事实依据。项目数据至少包含：用途、技术栈、软件设计架构、入口、顶层模块、未识别项和事实依据。每份 Rule 数据至少包含：必须遵守、相关知识路径、验证方式和更新门槛。

模板校验改为显式结构 allowlist：按模板路径解析 H1、H2 顺序、表头、固定文本和允许的占位符集合。任何额外标题、调换的表头、未声明占位符、普通文本中的动态项目事实、Mustache 变量、固定业务案例、固定命令、测试名、路径、平台或结论都会失败。黑名单正则仅作为补充诊断，不再是“模板合规”的证明。

`doctor` 对已初始化项目执行同一份结构合同：检查章节/表头、无未替换占位符、知识链接存在、文件树覆盖、架构图源与 SVG 同时存在、功能索引和目录互相可定位，以及 Rules 的五份固定文件和知识入口。

## Hook 作用域修复

已安装的 Plugin 对未接入 Harness 的项目必须无副作用。SessionStart 和 PreToolUse 先检测 `.codebuddy/harness.json`：存在时运行 Harness 行为；仅存在 `.codebuddy/onboarding-checklist.json` 时提示接入损坏并 fail-closed；两者均不存在时直接 no-op。不得以 `CODEBUDDY.md`、`.codebuddy/settings.json` 或通用 `.codebuddy/rules/` 作为标识。

因此未接入项目的 `git commit`、`.gitignore` 维护和会话启动不会读取 Harness 配置或执行门禁；已接入项目仍对门禁失败、直接写状态文件和忽略共享契约严格阻断。

## 验收

- 新建多模块项目的初始化测试证明：文件树路径骨架先写、每个可读文件被恰好分配并由负责人回写真实用途、无写入范围冲突，独立模块可并行，汇总和 Rules 仅在上游完成后启动。
- 初始化结束后，除 workflow 外的规范长期 Markdown 均存在、满足结构合同、无占位符且没有未登记文档。
- 工程模块、功能描述、项目总览和 Rules 的标题、章节、表头、相对知识引用与证据路径通过精确验证。
- 模板试验覆盖额外标题、错序标题、错表头、未声明占位符和偷塞动态事实的拒绝路径。
- 未接入 Harness 的项目通过 `git commit` Hook、SessionStart 和 `.gitignore` 修改回归；已接入项目仍会执行并阻断失败的 preCommit 门禁。
- `npm test --prefix plugins/coding-harness`、`npm run validate --prefix plugins/coding-harness`、发布包校验及 v0.7 四类独立验收全部通过后，才生成 `dist/ai-market-0.7.0.zip`。
